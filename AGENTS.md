# GitHub profile release

The release target is the [public profile](https://github.com/EndeavorEverlasting).
Its source is this repository's default-branch README and assets.

- Start with `python scripts/profile_release.py status --history` for the checked-out artwork, populated scenes, independent editorial revision, and commit history. Use `--json` when another tool consumes the results. The last fetched default reference can be stale; use `status --live` from a clean checkout of GitHub's default HEAD to verify the public artwork and repository invitation.
- Run `python scripts/profile_release.py status --compare v09` to see which scenes and repository invitation would change, then use the printed `restore` preview. Artwork restores keep current README prose. The linked Nexus invitation travels with its artwork. Older original artwork commits and newer Git registration commits are recorded separately.

- From the clean candidate commit, install `Pillow>=11,<14` if needed and run `python scripts/profile_release.py verify --base <full-origin-main-sha>` before landing. Fetch the default branch first and use its commit as the base. This runs the same scope, banner, artwork, and regression checks as Actions on `main`.
- Pull requests run the base commit's scope guard. The full hosted suite runs on `main` pushes and manual dispatch. Entire CLI records agent sessions and checkpoints. Keep any session capture separate from this public repository.
- When the operator has approved the visual and authorized landing, merge the verified change to the default branch in the same run. Carry that approval forward. A draft, branch preview, or green PR check is an intermediate result.
- After landing, run `python scripts/verify_profile_visuals.py --live` from the landed checkout. For visual changes, also open the public profile and verify the image's placement and visibility in the rendered page. Record the merged commit, public URL, and observed result. Investigate stale or missing artwork before claiming completion.
- Ask the operator only for a remaining visual decision or an actual authority boundary. Keep release verification and recoverable fixes with the executing agent.

## Reference-preserving visual revisions

- For revisions to an existing profile visual, recover the actual last-known-good artifact, explicit requested delta, previously accepted attributes and rejected variants before invoking a renderer. An adequate candidate is not automatically the new master. Keep original releases immutable; never replace a source with a description or a generated approximation.
- Default to a localized edit: preserve unrequested identity, pose, silhouette, proportions, composition, palette roles, optical effects, geometry and copy. A request to alter one layer is not permission to redesign other layers. For mathematically constructed visuals, change the underlying connected geometry, not a decorative overlay; validate topology, proportions and occlusion separately from aesthetic approval.
- Compare the actual candidate against the source and accumulated acceptance criteria at native size and intended display size. Reject changes outside the edit scope. If repeated corrections reveal a failure, reset to the preserved source and switch to a bounded deterministic edit where feasible rather than repeatedly resynthesizing accepted regions. Never turn a user into a reference courier when authorized source access is available.
- Export each requested asset independently and verify the actual readable file, dimensions and delivery surface. A rendered mockup, screenshot, blank response or claimed generation is not delivery. Keep candidate, adequate, approved, released and live-observed states distinct.
- Personal source images, private reference IDs, masks, full conversations and private aesthetic records stay outside this public repository. Load them only from the authorized private owner at execution time. The profile release system owns GitHub README artwork; other platforms' live account images and portfolio visuals have separate owners and approval gates. An orchestration skill is not an artifact owner.
- Continue to use the existing immutable release catalog, artwork quality floor, scope and visual gates for README releases. Do not weaken them or change the active release in a governance-only change.

### Profile image revision gate

This repository is the sole owner of EndeavorEverlasting personal-brand image revision tooling, including avatar and banner preparation; platform account publication and portfolio application deployment remain separate actions, not additional owners of this workflow. MoonWake orchestrates only; Momus is not a dependency. Before generating or editing, keep a private local revision packet outside Git and run `python scripts/profile_release.py revision <private-packet.json>`. The packet requires schema_version 1, source {path, sha256}, source_inspected, complete baseline, requested_delta, proposed (baseline plus only the authorized delta), rejected_variants, required_outputs mapping names to exact [width, height], and preservation_mode. For a protected-pixel edit use pixel_lock and an independently approved binary native mask with path, sha256 and mask_approved; do not silently downgrade to semantic mode. For review add native_candidate when pixel_locked, attribute_review mapping every attribute to status and evidence, and outputs mapping names to path and sha256. Run the same command with --review, then independently inspect actual images against the original and all retained criteria, including structural geometry when relevant. The gate does not certify aesthetic approval or the truth of review assertions. Do not regenerate rejected protected regions. Deliver each requested file separately; no account change without explicit approval. Run existing release verification and regression tests before landing. Private image packets, source bytes and personal reference identifiers never enter public Git.
